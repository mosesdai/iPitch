02 / 11

为什么现在必须升级

当前系统不是“不够聪明”，
而是被压缩成一次回答。

TODAY · SINGLE TURN
用户输入公司 + 碎片情报
单次模型调用一段长 Prompt
全部文件研究 + 刀刃 + 证伪

研究、溯源、反证、合成、验收被压缩进同一次输出。

01

来源不可靠

没有真实检索时，账本可能“看起来正确”，却无法确认链接、时效与来源等级。

02

阶段会缩水

一个回复里塞满 R1 文件，容易前后矛盾、局部变薄，也无法局部重跑。

03

门禁只看表面

文件名存在不代表内容达标；“有报告”不等于“报告通过验收”。

04

红队不独立

同一个模型既写方案又自我批评，很难真正推翻自己刚刚建立的观点。

05

无法团队化运行

浏览器直连模型 API，意味着 Key、CORS、审计、成本、长任务与历史记录都没有可靠的工程归属。

03 / 11

升级原则

我们需要的不是“更长的 Prompt”，而是更可信的生产过程。

01

事实先于叙事

每条关键数字回到来源、时间与可信等级，而不是让模型补全记忆。

02

独立角色互相制衡

研究者不能既是作者又是审稿人；反证和 Grill 必须有独立视角。

03

产物与过程都可审计

任何结论都能回看：谁做的、基于什么、过了哪些门禁、哪里被修复过。

核心变化

把 “Prompt” 从唯一的流程引擎，变成整个系统中一个受控的执行环节。

05 / 11

多 Agent 不等于多几个 Prompt

角色由 Skills 定义，
协作由后端编排。

每个 Skill 必须写清输入、输出、禁止事项和验收标准。这样每一步才可以被替换、测试和追责。

ROLE BRIEF

Research Planner

07 / 11

从“模型说完成”到“系统验收通过”

Programmatic Gate Checker
是系统的验收线。

它不会相信文件名，也不会相信模型的自评。它只读取产物内容，并给出可追溯的通过或失败理由。

quality_passport.json R1 / CONDITIONAL
必需文件齐全PASS
反证条目 ≥ 5PASS
冰山研究字数 ≥ 8000REPAIR
R2 iPod / shelf 分轨PASS
Artifacts读取产物
Check程序验收
Route定位失败阶段
Repair定向补强
不通过
不交付
08 / 11

团队级运行的基础设施

Agent 的“答案”不是一段文本，
而是一组可管理的产物。

server-data/ipitch-runs/
└─ {run_id}/
├─ run.json 运行主记录
├─ stages.json 阶段状态与重试
├─ quality_passport.json 门禁结果
└─ artifacts/ 最终交付
可预览可下载可历史追溯可局部重跑

10 / 11

分阶段落地，不一次性过度工程化

先让 R1 跑通且可观察，
再把能力扩展到真正的团队系统。

01

POC

后端 + Cursor Agent

  • 创建 run 与异步进度
  • R1 拆为 4–6 个 stage
  • 产物写入服务器磁盘
  • 基础 Gate Checker
先验证闭环
02

TRUST

真实检索 + Source Ledger

  • 检索 / MCP / 企业资料源
  • 每条事实带来源和时效
  • 研究只能引用账本事实
建立可信度
03

RIGOR

独立 Reviewer + Repair

  • ifalsify / Grill 独立 run
  • 门禁失败自动定向修复
  • 保留修复理由
建立严谨度
04

TEAM

团队级 Pitch OS

  • 案例库与版本管理
  • Sales 回填与轮次恢复
  • 评测集与效果对比
建立复利

建议的决策

批准一个 R1 POC，
验证 iPitch 能否成为可信的 Agent 工作流。

这次升级的价值，不是让输出看起来更“AI”，而是让关键商业判断从生成到交付都能被解释、质询与复盘。

本次要确认
  • 采用 Node / Vercel 级别轻后端
  • 使用 Cursor SDK 连接 Skills 仓库
  • R1 优先，磁盘 Artifact Store 优先
  • Gate Checker 作为不可省略的验收层
